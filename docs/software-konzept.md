# Software concept: firmware, web UI, operation

Status: 2026-11-06 · Draft for discussion. Complements [hardware-konzept.md](hardware-konzept.md), section 7.
Firmware: **Rust (std on ESP-IDF)** on the ESP32-C6, structure in [firmware-architecture.md](firmware-architecture.md).

## 1. Goals and guard rails

- **Playable without a phone.** Lever on = round with the last selected mode. The web UI is an
  add-on, not a prerequisite.
- **Two network modes**: in a known Wi-Fi (phones keep internet access) or as its own
  hotspot (SoftAP) when no known network is available. Switching happens automatically.
- **Roles**: normal users and admin. The admin sets up Wi-Fi networks, sets limits and critical
  settings. Deliberately simple at first, but built so that a later
  multi-user system (profiles, own modes per person) is only **added**, not rebuilt.
- **Everything offline.** In hotspot mode there is no internet, so no CDN either. All files
  of the web UI live in the flash of the ESP32-C6.
- **Development in parallel with the hardware**: game logic, server and web UI also run on the PC
  with a simulated motor (see 9).
- **Safety before convenience for the motor**: limits are always enforced by the server, never by the UI.

## 2. Language and framework

### 2.1 Constraints

ESP32-C6-MINI-1: one RISC-V core at 160 MHz, **512 KB SRAM** (Wi-Fi and BLE need a large part of it),
**4 MB (N4) or 8 MB (H8) flash**. Nothing is time-critical: PWM, ramps and measurements run on a 10–50 ms grid;
the PWM itself is generated by hardware (LEDC).

### 2.2 Decision

**Rust, std on ESP-IDF** (esp-idf-svc / esp-idf-hal / esp-idf-sys). Rationale and rejected alternatives:
[firmware-sprache.md](firmware-sprache.md). Crates, threads, storage and tests: [firmware-architecture.md](firmware-architecture.md).

### 2.3 Clean separation

The game logic knows no hardware and no network (separate crate, also runs on the PC and in the browser). The web UI
only speaks the documented protocol (see 7). A later change of the firmware base (e.g. to no_std)
therefore only affects the firmware crate. **Web UI and protocol stay.**

### 2.4 Web UI technology

- **Preact + htm** (about 5 KB, JSX-like without a build step) as a local file in the project.
  Alternative: plain JavaScript with Web Components. No React, no Tailwind CDN.
- Optional build via `just web`: bundle files, minify, **gzip**. The ESP serves the
  `.gz` files directly with `Content-Encoding: gzip`. Target: below 100 KB compressed.
- **Caution, no HTTPS**: Self-signed certificates cause warnings on every phone, and there is no trusted
  certificate for a device in the local network. A TLS server would run on the C6 (ESP-IDF
  `esp_https_server`), but it costs RAM per connection and does not solve the certificate problem.
  In an insecure context the browser lacks: Web Crypto (`crypto.subtle`), Service Worker / PWA installation,
  Wake Lock (keep screen on). Vibration (`navigator.vibrate`) works on Android, not on iOS. The UI must
  work without these. WebAssembly (mode preview) works without HTTPS too.

## 3. Network

### 3.1 Startup sequence

```
Wake up / power on
   │
   ├─ Lever gesture at start? (flip 5× quickly) ──► force hotspot (recovery)
   │
   ├─ Scan → known networks by priority and signal strength
   │      └─ connect (max. 10 s each) ──► OK ──► STA mode, mDNS "louie-xxxx.local" (alias "louie.local")
   │
   └─ no success ──► hotspot "Louie-XXXX" (XXXX from MAC), captive portal
                       └─ every 2 min search for known networks in the background,
                          but only when no round is running and no client is connected
```

- **The network mode never changes during a round.** If the Wi-Fi drops, the
  round continues (the lever always works); it reconnects afterwards.
- Several networks can be stored (home, grandma, holiday house), with priority.
- **No fixed IP** as in v1 (`.66` was a collision risk in other networks). Instead
  mDNS `louie.local` (with several devices `louie-xxxx.local`) and DHCP.

### 3.2 Hotspot and captive portal

- WPA2 with a **device-specific random password** (generated at first start and stored in NVS, not derived from the MAC,
  because the firmware is open; firmware-architecture.md 5.5), printed on a sticker
  with **two QR codes**: "Join Wi-Fi" (`WIFI:S:Louie-XXXX;T:WPA;P:…;;`) and
  "Open controls" (`http://192.168.4.1`). The admin can also make the hotspot open.
- Captive portal: a small DNS server answers all requests with 192.168.4.1. The phones then
  show "Sign in to network" by themselves.
- Known problem: the sign-in window (iOS "Captive Network Assistant", Android portal view)
  is a restricted browser that closes when you leave it. The portal page therefore shows only
  one large button **"Open in browser"** plus the hint "Keep connection despite missing
  internet". The actual UI runs in the normal browser. *Test with iOS and Android in the prototype.*
- Set the maximum number of hotspot clients high enough (target 8; ESP-IDF allows up to 10).

### 3.3 Setting up a new Wi-Fi (admin)

1. The admin is connected via the hotspot and selects "Add Wi-Fi" → list from scan.
2. The ESP tests the credentials **in AP+STA mode**, so the hotspot stays up.
3. The result appears live in the UI: "Connected to *Home network*. Louie is reachable there at
   http://louie.local (192.168.1.57)." Buttons "Switch now" or "Keep hotspot".
4. The hotspot is switched off only after confirmation. Wrong password → error message,
   nothing is lost.

Admin option: **keep the hotspot open in addition to the Wi-Fi** (for guests without access to the
home network). Costs some RAM and airtime, therefore off by default.

## 4. Roles and permissions

> Revised in [web-ui-konzept.md](web-ui-konzept.md) (roles, game master handover, player phones).

### 4.1 Roles

| Role | How to get it | May |
|---|---|---|
| **Guest** | Open the page | See status |
| **Player** | Choose seat/colour (no password) | Boosts etc. as the mode allows |
| **Game master** | Claim the free role or receive it by handover; one per round | Choose mode, release/stop round, mark players as out |
| **Admin** | Enter password (session expires after 30 min idle) | Everything incl. Wi-Fi, limits, model profile, update, factory reset |

Player and game master are **roles in the running game**, not accounts. Admin is
the only protected level. Which permissions players have (e.g. "save modes", "become game
master") is set by the admin (see 4.3).

### 4.2 Admin access

- **Initial setup**: At first start you set the admin password in the wizard (see 6.1).
  So that nobody within radio range gets there first, this is confirmed by **flipping the lever**
  (physical access = owner).
- **Forgotten password**: A lever gesture at start (e.g. flip 10×) resets the admin password.
  Game modes stay; Wi-Fi networks are also deleted for security reasons.
- Storage: salted hash (SHA-256, iterated several times) in `config.json`. Without HTTPS the
  password travels over Wi-Fi in plain text. For a toy in a WPA2 network this is acceptable, but
  the UI does not hide it ("do not use the same password as for the home network").
- Brute-force brake: 1 min lock after 5 failed attempts.

### 4.3 Technical preparation for multi-user

So that multi-user is only an add-on later:

- Each connection has a **session** (random token, 128 bit, in `localStorage` and as a cookie).
  Reload or short Wi-Fi drop → same seat, same role.
- Permissions are a **list of rights**, not fixed roles in the code:
  `view`, `play`, `lead`, `modes.create`, `modes.delete_own`, `admin`.
  A table role → rights is part of the configuration.
- Stored objects (modes) have a field `owner` from the start (session, later profile ID).
- Stage 2: **profiles** with nickname, colour, emoji, without password. The device remembers profiles per
  phone via the token. This enables: own modes, statistics ("Who flies out most often?").
- Stage 3 (only if needed): profiles with PIN, more roles.

## 5. Game

### 5.1 States

```
          Lever off / stop in UI
   ┌────────────────────────────────────┐
   ▼                                    │
 READY ──(choose mode)──► READY ──lever on──► RUNNING ──end per mode──► END ──► READY
   ▲                                    │  ▲
   │                                    ▼  │
   └──── idle 15 min ──► SLEEP        PAUSE (game master)
```

- Change mode only in READY/END and with the lever "off".
- Lever is "on" at wake-up → **no** round starts, the UI shows "Set lever to off".
  After that, lever on = start. This prevents a surprise start at wake-up.
- Optional (admin setting): **start only after release** by the game master. Default:
  the lever starts directly.
- The lever is in series with the motor and therefore **always disconnects it in hardware**. The
  stop never depends on the software.

### 5.2 Game modes as data

> Authoritative is **schema 2** in [modus-baukasten.md](modus-baukasten.md) section 2. The example below only shows
> the basic idea (older format).

A mode is a JSON description, not code. Building blocks (evolved from v1 `config.yml`):

```json
{
  "id": "chaos",
  "name": "Chaos",
  "owner": "builtin",
  "speed": {"type": "random", "min": 30, "max": 90, "change_every_s": [2, 6]},
  "reverse": {"chance": 0.10, "duration_s": [0.5, 1.5]},
  "pause":   {"chance": 0.05, "duration_s": [1, 2]},
  "ramp_up": {"to": 100, "over_s": 120},
  "boost":   {"who": "out", "strength": 25, "duration_s": 2, "cooldown_s": 10, "per_round": 3},
  "rewind":  {"who": "all", "duration_s": 0.8, "cooldown_s": 20, "per_round": 2},
  "end":     {"type": "lever"}
}
```

- **Speeds in percent** of the allowed range from the model profile
  (0 % = minimum voltage, 100 % = rated voltage, above that only up to the turbo limit).
  A mode therefore runs unchanged on old and new Louie and on Chewie.
- The server **clamps** every value to the admin limits, also for boosts and test drive.
- **Reverse driving**: allowed, but by default only in small doses. You can hardly defend yourself against
  a Louie turning backwards, so long reverse phases are frustrating.
  The server enforces (admin limits, defaults in brackets): max. duration per reverse burst
  (1.5 s), minimum gap between two bursts (8 s), max. share of the round time (10 %).
  Direction changes always go through a ramp (brownout, see hardware concept 5.1).
- **Rewind (multi-user)**: Each player can trigger a very short reverse burst from the phone
  (about 0.5–1 s) to annoy others. Limited by quota per round, cooldown
  and the global reverse limits above. Simultaneous requests do not add up.
- Built-in modes (proposal): Classic, Relaxed, Escalation, Random, Chaos (with reverse),
  Last Chicken Standing (boosts for players who are out).

### 5.3 May users save modes?

Proposal: **Yes, on by default, but can be switched off.** Rationale: thanks to clamping to the limits,
modes cannot break anything, and "build your own mode" is fun for kids.

- Anyone may adjust a mode for the next round without saving ("this round only").
- Saving creates a new mode with `owner`. Only the creator or the admin may delete it.
- The admin can: switch off saving for users, lock modes, set a maximum number
  (flash limit, e.g. 30).
- Built-in modes are read-only and can only be copied.

## 6. User experience

Mobile first, portrait, large controls (≥ 48 px), one-handed, dark and light theme,
multilingual with English as the source language (texts centralised; browser language detection and manual
switch, see web-ui-konzept.md 9; the PoC stays German). Live state via WebSocket; on
connection loss a clear notice and automatic reconnect.

### 6.1 Initial setup (wizard in hotspot)

1. Choose model: old Louie / new Louie / Chewie (pictures)
2. Direction of rotation: "Lever on. Does Louie turn the right way?" → Yes / No (direction is stored)
3. Set admin password, confirm with the lever
4. Optional: set up home Wi-Fi (see 3.3)
5. Done: hint about the QR sticker and `louie.local`

### 6.2 Main views

> Revised in [web-ui-konzept.md](web-ui-konzept.md), clickable in [web/poc/index.html](../web/poc/index.html).

| View | Content |
|---|---|
| **Start / lobby** | Large status ("Ready – flip the lever"), current mode as a card, seats 1–4 in chicken colours to tap, battery level, game master role free/taken |
| **Round (player)** | Large boost button with cooldown ring and remaining count, current speed, "out" status |
| **Round (game master)** | Live speed, mark players as out, pause, stop |
| **Modes** | List, details, "Adjust" with sliders and preview curve, "Test drive" (10 s, only with lever on) |
| **Admin** (behind lock icon) | Wi-Fi, model & limits, user permissions, device, update, diagnostics |

### 6.3 Admin settings

| Area | Settings |
|---|---|
| Wi-Fi | Add/remove networks/priority, hotspot name and password, keep hotspot open in addition, hostname |
| Model & limits | Model profile, minimum and rated voltage, turbo limit, max. ramp (V/s), direction of rotation |
| Reverse | allowed yes/no, max. duration per burst, minimum gap, max. share of the round, rewind for players yes/no, quota per player |
| Power | Idle time until sleep, undervoltage warning and shutdown |
| Permissions | Save modes, become game master, start only with release |
| Device | Change admin password, back up/restore configuration (JSON), restart, factory reset |
| Update | Upload firmware file (OTA, see 8.3) |
| Diagnostics | Battery, motor current, lever state, RSSI, free memory, recent errors |

### 6.4 Details that are often forgotten

- **Sleep despite open tabs**: Phones keep WebSockets open in the background. Sleep therefore depends
  on "no round and no interaction for 15 min", not on "no client connected".
  1 min before, a notice in the UI with "Stay awake".
- After sleep the UI shows "Louie is sleeping – flip the lever to wake" and reconnects.
- **Status LED** shows the network mode (e.g. slow blink = hotspot, on = Wi-Fi, fast = error),
  so you know where to look without a phone.
- Battery low: warning in the UI, the round ends cleanly before shutdown.

## 7. Browser ↔ device interface

- **REST (JSON)** for configuration and management, **one WebSocket** `/ws` for live state
  and actions during the game. The server is the single source of truth; clients send
  requests, the server checks permissions and limits.
- State is sent on changes, during the game at most 10× per second, as one JSON for all clients.
- Extensions (game master handover, players, wireless buttons, protocol version):
  [firmware-architecture.md](firmware-architecture.md) 5.3. The browser computes the mode preview (WebAssembly).

| Method | Path | Right |
|---|---|---|
| GET | `/api/state` | view |
| POST | `/api/session` (nickname, seat) | – |
| GET / POST | `/api/modes` | view / modes.create |
| PUT / DELETE | `/api/modes/{id}` | creator or admin |
| POST | `/api/admin/login`, `/api/admin/logout` | – / admin |
| GET / PUT | `/api/admin/config` | admin |
| GET | `/api/admin/wifi/scan` | admin |
| POST / DELETE | `/api/admin/wifi`, `/api/admin/wifi/{ssid}` | admin |
| POST | `/api/admin/update`, `/api/admin/reboot`, `/api/admin/reset` | admin |

WebSocket messages (selection):

```
Server → Client: {"t":"state", "phase":"running", "speed":62, "mode":"chaos", "lever":true,
                  "battery":3.85, "players":[…], "leader":"s_ab12"}
                 {"t":"event", "kind":"boost", "seat":2}
Client → Server: {"t":"boost"}  {"t":"rewind"}  {"t":"claim", "seat":3}  {"t":"lead"}
                 {"t":"select_mode", "id":"chaos"}  {"t":"out", "seat":1}  {"t":"stop"}
```

## 8. Firmware structure

Details: [firmware-architecture.md](firmware-architecture.md). Only the principles here.

### 8.1 Layers

- **Core** (`louie-core`): game state, mode interpreter (schema 2), jokers, limits, permissions. No hardware and
  no network; runs on the ESP, on the PC and as WebAssembly in the browser.
- **App** (`louie-app`): sessions, roles, WebSocket hub, REST router, wireless button inputs. No hardware,
  shared by firmware and simulator.
- **Firmware** (`louie-fw`): HAL (motor, lever, battery, current, LEDs, inputs, BLE), Wi-Fi, web server, storage, OTA.
- **Motor safety**: separate thread with watchdog. If it receives no setpoints for 500 ms, it drives to 0.
  Ramps and limits apply in this lowest layer, whatever happens above.
  The ESP's hardware watchdog restarts a hung firmware; the motor then stops.
- **Stall**: The DRV8213 reports the motor current via IPROPI. Current above the threshold for longer than about 0.5 s →
  motor off, stop the round, error in the UI.

### 8.2 Storage

| Content | Location |
|---|---|
| Web UI and language files (gzip) | in the firmware (updated together) |
| `config.json`: model profile, limits, permissions, admin hash, power | LittleFS |
| `devices.json`: paired wireless buttons | LittleFS |
| `modes/*.json`: own modes (built-in ones are in the firmware) | LittleFS |
| Wi-Fi credentials, hotspot password | NVS |
| later: `profiles.json` | LittleFS |

Write only on changes, always to a temp file first, then rename (no broken JSON on
power loss). Wi-Fi credentials are stored **only on the device**, never in Git.

### 8.3 Updates

Real OTA with two app partitions and automatic rollback to the previous version if the new firmware
does not start cleanly. The firmware contains the web UI, so an update replaces both together. On the
N4 module (4 MB) this works as long as the firmware stays below about 1.8 MiB (partition tables:
firmware-architecture.md 6.1). Flashing via USB-C (J4) remains as an emergency path.

## 9. Development in parallel with the hardware

- `just sim`: starts the simulator on the PC with the same app layer as the firmware and simulated
  hardware: lever (key or button in the UI), motor, battery, wireless buttons. In the simulator the web UI shows a
  small animated Louie. This allows finishing the UI and game logic before the board exists.
- `just test`: tests for game logic, modes (golden tests), limits, permissions.
- Testing several phones: start the simulator in the home network and connect real phones.
- Before the board, the same firmware runs on a breadboard setup with an ESP32-C6 board
  ([test-hardware.md](test-hardware.md)). Commands and order: firmware-architecture.md 10 and 11.
